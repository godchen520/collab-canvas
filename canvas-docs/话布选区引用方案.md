# 话布选区引用方案

> 设计稿 v2 · 2026-09-14 · 待评审
> v2 变更：生命周期定为「创建 → 注入 → 本轮结束销毁」；去掉上限与 TTL

---

## 一、要解决的问题

从话布划词点「问 AI」时，插进输入框的是：

```
> 写入方基于哪一版
```

**只有"哪段文字"，没有"哪一处"。** 由此产生三个问题：

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 同一段文字在文档里出现多次 | AI 分不清是哪一处，只能**猜** |
| 2 | 有些文档**没有小节** | 连"按标题定位"这条退路都没有 |
| 3 | 会话换一个（或 DSH 重启） | 上一轮定的约定没人记得 |

而"猜"的代价是**改了错的地方**，且用户当场看不出来。

---

## 二、方案总览

```
① 你划词 → 点「问 AI」
        ↓
② 客户端捕获选区 Range，POST 给 host
   （Range 在浏览器里，必须送出来才能被 AI 读到）
        ↓
③ host 存进内存表：引码 → 选区详情          【创建】
        ↓
④ 引用插入输入框（多了一个短引码，模型完全不需要理解它）：
        @话布优化 ⟨引码:7⟩ > 写入方基于哪一版
        ↓
⑤ 你发送 → host 在 agent/pre-step 钩子里扫到引码
        ↓
⑥ 查表 + 核对（版本号 → 上下文指纹）
        ↓
⑦ 把结果作为【插件来源的消息】追加进上下文    【注入】
        ↓
⑧ AI 直接看到「哪篇、哪一处、是否还有效」—— 不需要它主动去取
        ↓
⑨ turn/end → 回收本轮注入过的引码          【销毁】
```

**关键在第 ⑤⑦ 步**：信息是**被注入的**，不是 AI"想到去查"的。

---

## 三、选区记录的生命周期

**定性：这是一条"待消费的消息"，不是一份缓存。**

```
创建   点「问 AI」时写入
注入   每次 pre-step：本轮消息含引码且记录还在 → 注入
销毁   turn/end 时，回收【本轮注入过的】那几条
```

### 为什么销毁时机是「本轮结束」而不是「注入后立刻」

因为一个**尚未验证的未知**：追加的消息**是否延续到后续步骤**？

`dsh-time-context` 带节流参数，**暗示可能不延续**。

| 销毁时机 | 风险 |
| --- | --- |
| 注入后立刻 | 第 1 步看到定位 → 第 2 步读文档时**已经没了** → 编辑时可能忘了是哪一处 |
| **本轮结束** ✅ | 每步都能重新注入，本轮内始终看得到；一样不累积 |

`turn/end` 是 DSH 的正式事件，实现上不比"立刻"复杂。

### 明确不做的三件事

| 不做 | 理由 |
| --- | --- |
| **上限（原稿 200 条）** | 记录只在用户点「问 AI」时创建，**条数由用户行为天然限制**，没有失控向量 |
| **TTL（原稿 24 小时）** | 生命周期由**事件**（turn/end）决定，不由**时钟**决定 |
| **落盘** | 重启后本来就不需要 |

### 边角情况

| 情况 | 结果 |
| --- | --- |
| 引用了，一直放聊天框很久才发 | ✅ **天然满足** —— 从没被注入过，记录一直在表里等着 |
| 一轮里引用多条 | ✅ 每条一个引码，各自注入、各自回收 |
| A 会话引用没发，B 会话又引用 | ✅ 记录按引码存，**与会话无关**，互不影响 |
| 引用了但永远不发 | ✅ 留在内存里，**重启即消失**，不需要任何清理 |
| **本轮异常中断**（重试 / 用户按停止） | ⚠️ 记录已回收 → 重发时只剩标题兜底 → **AI 会问用户一句**。不会改错，只是多问 |

## 四、三个部件

### 部件 1 · 客户端：捕获选区

现有基础：划词栏本来就存了选区（`savedRangeRef`），**捕获几乎零成本**。

点「问 AI」时额外计算并 POST：

| 字段 | 用途 |
| --- | --- |
| `canvasId` | 哪篇 |
| `docVersion` | 过期校验第一层（免费，已有） |
| `offset` + `length` | 精确位置 |
| `before` / `after`（各 24 字符） | 过期校验第二层（指纹） |
| `selected` | 选中的原文 |
| `heading` | 最近的小标题（无则为空） |

### 部件 2 · host：选区表（内存）

```js
Map<token, {
  canvasId, title, path,
  docVersion, offset, length,
  before, after, selected, heading,
  at            // 时间戳：只用于向用户解释"多久之前选的"
}>
```

**同一 DSH 进程内跨会话共享**（它是 host 内存，不是浏览器状态）。

**上限 500 条**，超了丢最旧的：

```js
if (SEL.size >= 500) evictOldest()
```

正常永远碰不到（要 500 次「引用了但不发送」）。加它的唯一理由是**防失控**：
万一客户端有 bug，在某条非点击路径上重复 POST，表会被无限撑大 ——
**这不是防用户，是防作者自己的代码出错**。

注意：淘汰的是**记录**，不是引码编号 —— 编号照旧往前走。

### 部件 3 · host：`agent/pre-step` 注入

官方机制，有官方先例（`@deepseek-ai/dsh-time-context`）：

```js
ctx.on("agent/pre-step", async ({ agent, turn, step, signal }, next) => {
  const decision = await next();
  const token = findSelToken(这轮的用户消息);      // ★ 只扫本轮
  if (!token) return decision;
  const record = SEL.get(token);
  if (!record) return decision;
  const text = renderSelContext(record, currentContent(record));
  markConsumed(token);                            // 记下"本轮注入过"，供 turn/end 回收
  return { ...decision, messages: [...decision.messages, createUserMessage({
    content: [{ type: "text", text }],
    source: { kind: "plugin", plugin: name, form: "snapshot", sections: [{ name, text }] }
  })] };
}, { prepend: true });

ctx.on("turn/end", ({ turn }) => { /* 回收本轮注入过的 token */ });
```

**不依赖 `sessionProjections`**（那个服务只有 `dsh-tool-cordis` 提供，风险高）—— 扫描消息文本就够。

> ⚠️ **必须只扫本轮的用户消息**，不能扫整个历史：否则历史里所有旧 token 每轮都会重新注入一遍，变成噪音。

## 五、关键设计决策

### 决策 1 · 用「上下文注入」而不是「工具」

|  | 工具方案 | **注入方案（采用）** |
| --- | --- | --- |
| 可发现性 | 靠 token 里带工具名 + 描述 | ✅ **不依赖**——信息是塞进去的 |
| 模型忽略的风险 | 存在（它可能不调） | ✅ 基本消除 |
| 需要新工具 | 要 | ✅ 不要 |

> "没有机制能强制模型调用工具"是对的，但**注入不属于"调用工具"这条路**。

### 决策 2 · 引码：短、中文、递增编号

```
@话布优化 ⟨引码:7⟩ > 写入方基于哪一版
```

引码的**唯一职责**是让 host 钩子找到记录。既然注入是自动的，**模型不需要理解它**。

**形态**：`⟨引码:<递增数字>⟩`

| 要素 | 选择 | 理由 |
| --- | --- | --- |
| 外壳 `⟨⟩` | 保留 | 罕见字符，正常文本里几乎不可能自然出现。`【】` 与作者回复里的小标题习惯冲突；`《》` 在中文语境里太常见（书名） |
| 名字 `引码` | **生造词**，不用「引用」 | 「引用」是常用词，消息里本来就可能出现"引用: 这段"这类写法；引码永不自然出现，**零歧义** |
| 内容 | **递增计数器**（1、2、3…） | 记录不设上限（引用了永不发的会一直留着），随机值理论上会撞号；计数器零成本且绝对唯一 |
| 用中文 | 保留 | 机制正常时引码不重要；**机制失败时**（如重启后记录丢了）模型看到 `⟨引码:7⟩` 至少能判断"这里有个引用标记没解析出来"，更可能来问，而不是当成正文照旧猜 |

#### 引码与记录怎么回收

两者都要分清**进程内**与**跨重启**：

| 对象 | 进程内 | 跨重启 |
| --- | --- | --- |
| **记录** | turn/end 回收本轮注入过的；「引用了不发送」的留到上限淘汰 | ✅ 随进程清空（内存 Map，不落盘）|
| **引码编号** | 只增不减 | ✅ 全部回收，计数器从 1 重新开始 |

**为什么进程内不复用编号**：会与「还在输入框里没发送」的旧引码撞号。

```
你引用了     → ⟨引码:7⟩ 躺在输入框
（中间又发生很多次引用）
你又引用     → 若编号回头用 7 → 两条记录打架
```

**为什么跨重启可以整体回收**：重启后记录全清，旧引码已经没有对应记录了。
选它而不是「发送后立刻回收该号」，理由是**零实现成本** —— 内存本来就没了，
计数器自然从 1 开始；而按号回收要维护一个空闲号池，还得处理归还逻辑。

**重启后的同号**：重启后可能产生与历史消息里相同的 `⟨引码:1⟩`。会不会误注入？
**不会** —— 钩子只扫**本轮**的用户消息（见第四章），历史根本不会被扫到。

**编号无限增长有没有问题**：没有。JS 安全整数是 2^53 ≈ 9000 万亿，
每秒引用一次也要 2.85 亿年；1000 次之后只多 2 个字符；Map 查找 O(1)，与编号大小无关。
所以「回收」的价值是**语义干净**，不是性能。

### 决策 3 · 过期校验分三层

```
选区时记录 docVersion

改之前：
  ① 版本号相同？ → 直接可信，用偏移量（零成本，绝大多数情况）
  ② 版本号变了？ → 用 before/after 指纹核对上下文
                     ├─ 对得上 → 照改
                     └─ 对不上 → 报「引用已过期，请重新选择」
```

**为什么不用时间戳做判定**：时间只能回答"多久之前选的"，**回答不了"内容有没有动过"**。一秒后可能已变，一周后也可能没变。

时间戳保留，但只用于向用户解释。

**为什么版本号是免费的第一层**：并发保护（`knownVer`）已经在用同一套版本号。

### 决策 4 · 引用里保留标题做兜底

```
@话布优化 ⟨引码:7⟩ > 写入方基于哪一版
   ↑ 重启后仍有效      ↑ 重启后失效
```

DSH 重启 → 记录没了 → 但 AI 仍知道是**哪篇文档**，只是不知道哪一处 → 降级成"问用户一句"，而不是彻底瞎猜。

**冗余是刻意的**：引用给"哪篇"，注入给"哪一处"，任何一边缺失都还能工作。

## 六、注入内容长什么样

要短——它每步都在上下文里。

```
【话布选区】引用来源：话布优化 · 第十四节
选中文字：「写入方基于哪一版」
位置：当前文档第 603 行（有效）
```

失效时：

```
【话布选区】引用来源：话布优化
选中文字：「写入方基于哪一版」
⚠️ 该选区已失效（文档已改动，上下文对不上）。请让用户重新选择，不要凭猜测定位。
```

## 七、实施步骤（每步可独立验证）

| 步骤 | 内容 | 验证方式 |
| --- | --- | --- |
| **1** | 最小钩子：`agent/pre-step` 里追加一句固定文字 | 看模型能否复述 → 证明注入通路可用 |
| **2** | 选区表 + 客户端 POST | 调 host 接口确认写入；日志可查 |
| **3** | 引码写进引用 + 钩子扫到它 | 端到端：引用一次，看注入内容是否出现 |
| **4** | 过期校验（版本号 + 指纹） | 改动文档后再引用，看是否正确报失效 |
| **5** | turn/end 回收 | 连发两轮，确认第二轮不再注入旧引码 |

**先做第 1 步**——它是整条路的地基，成本最低。**第 1 步不通，后面全部作废**，及时止损。

## 八、风险与未知

| # | 风险 | 说明 | 应对 |
| --- | --- | --- | --- |
| 1 | **追加的消息是否延续到后续步骤** | `dsh-time-context` 的节流参数暗示**可能不延续** | 第 1 步即可验证；不延续就每步注入（内容短，代价可控） |
| 2 | 上下文成本 | 每步几十个 token | 内容压到 3 行以内；只在含 token 的轮次注入 |
| 3 | `agent/pre-step` 是否稳定契约 | 官方包在用，未见文档 | **第 1 步先验证；失败即放弃本方案** |
| 4 | 非本会话写入 | 另一会话改了文档 | 已有 `knownVer` 并发保护覆盖 |
| 5 | 首轮改写错误 | AI 误判注入内容 | 注入文本明确写出"是否有效"，失效时明令不许猜 |

## 九、明确不做

- ❌ 不写 `canvas_selection` 工具（注入方案下不需要）
- ❌ 不落盘、不设上限、不设 TTL（重启即消失，无需清理）
- ❌ 不支持手打引用（用户已排除该功能）
- ❌ 不跨 DSH 进程共享

## 十、与已有机制的关系

| 已有机制 | 本方案的关系 |
| --- | --- |
| 引用带 `@"绝对路径"` | **保留**（解决"哪篇"） |
| 并发保护 `knownVer` | **复用**其版本号（解决"有没有变"） |
| 重复画布修复 | 前置条件（否则"哪篇"本身就不唯一） |
| `present` 卡片 | 无关，各司其职 |
