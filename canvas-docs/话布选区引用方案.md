# 话布选区引用方案

> 设计稿 v3 · 2026-09-14 · 待评审
> 
> **v3 变更（重大，推翻了 v2 的两条主干）**
> 
> 
> |  | v2 | v3 |
> | --- | --- | --- |
> | 引用长什么样 | 纯文字 `⟨引码:7⟩` | **官方引用胶囊**（带图标的小色块） |
> | 什么时候展开 | 服务端 `agent/pre-step` 钩子注入 | **发送那一刻，官方来问话布** |
> | 用户操作 | 点「问 AI」→ 出现一串字 | 点「问 AI」→ 自动走完官方两步 → 出现胶囊 |

## 一、要解决的问题

### 1.1 老问题：AI 分不清"哪一处"

从话布划词点「问 AI」时，插进输入框的是：

```
> 写入方基于哪一版
```

**只有"哪段文字"，没有"哪一处"。** 由此产生三个问题：

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 同一段文字在文档里出现多次 | AI 分不清是哪一处，只能**猜** |
| 2 | 有些文档**没有小节** | 连"按标题定位"这条退路都没有 |
| 3 | 会话换一个（或 DSH 重启） | 上一轮定的约定没人记得 |

而"猜"的代价是**改了错的地方**，且用户当场看不出来。

### 1.2 新问题：引用在输入框里"不像个东西"

v2 打算把引用写成 `⟨引码:7⟩` 这样的纯文字。动手前实测发现两个毛病：

- **看着像乱码**，用户不知道那是什么
- **能被误删、误改** —— 它就是普通字符，退格键一按就少一半，还毫无提示

而 DSH 输入框本来就有一套更好的东西：`@文件`、`@会话`、图片，都会显示成**带图标的小胶囊**。

引用理应长成那样。

## 二、方案总览

```
① 你划词 → 点「问 AI」
        ↓
② 客户端捕获选区，留一条记录（编号 #7）              【创建】
        ↓
③ 客户端自动走官方两步：打开菜单 → 选中 #7
   （这两步原本是"用户打 @ + 点一下"，现在由话布代劳）
        ↓
④ 输入框里出现一个胶囊：
        [图标] 写入方基于哪一版
        ↓
⑤ 你发送 → 官方逐个胶囊调用话布的【翻译规则】
        ↓
⑥ 翻译规则查记录，输出**两行**引用（路径 + 原文）
        ↓
⑦ 胶囊被替换成这两行，拼进最终消息
        ↓
⑧ AI 看到「哪篇、第几行、是不是有多处」；
   要精确位置就问 canvas_locate 工具
```

**关键在第 ⑤⑦ 步**：既不是 AI"想到去查"，也不是钩子"硬塞进上下文"，

而是**官方在发送时主动来问话布："这个胶囊代表什么？"**

v2 的注入方案要赌两件不确定的事（钩子是否稳定、追加的消息是否延续到后续步骤）；

v3 这两件事**都不需要赌** —— 它是 prompt 正文的一部分，天然就是完整的。

## 三、块状图：谁做什么

| 部件 | 在哪 | 做什么 | 新增/复用 |
| --- | --- | --- | --- |
| 1 · 捕获选区 | 客户端 | 算出"哪篇、第几行、选的是第几处" | 复用现有划词栏（`savedRangeRef`） |
| 2 · 引用源 | 客户端 | 告诉输入框"话布也有东西可引用" + 翻译规则 | **新增** |
| 3 · 自动两步 | 客户端 | 替用户打开菜单、选中那一项 | **新增** |
| 4 · 记录表 | 客户端内存 | 编号 → 选区详情 | **新增**（不落服务端） |
| 5 · **定位工具** | **服务端** | 回答"到底是哪一处 / 有没有失效" | **新增**（第 6 步；必须在服务端 —— 它读的是**当前**文档） |

**第一版没有服务端部件**，这是 v3 相对 v2 最大的减法；
后来补回一个（第 6 步的定位工具），因为"定位"与"是否失效"都得看当前文档。

## 四、部件 1 · 捕获选区

现有基础：划词栏本来就存了选区（`savedRangeRef`），**捕获几乎零成本**。

点「问 AI」时额外计算并留存：

| 字段 | 用途 |
| --- | --- |
| `canvasId` / `title` / `mention`（路径） | 哪篇 |
| `version` | 文档版本号（留着做前后比对） |
| `offset` + `length` | 精确位置（客户端内部用） |
| `line` | 第几行 → 写进引用标签 |
| `dupCount` | 原文在全文出现几次（允许重叠） |
| `ordinal` | **你选的是第几处** → 写进引用标签；跨端口径一致，是定位的关键 |
| `selected` | 选中的原文 |
| `heading` | 最近的小标题（无则为空） |

> 前后文指纹（`before` / `after`）**已不记录** —— 过期校验改由定位工具读当前文档来做。

**存在哪里**：第一版存**浏览器内存**。

为什么可以先不落服务端：记录只服务于"翻译"，而翻译发生在浏览器里；

刷新页面后胶囊本身也会退化（见决策 5），不会出现"胶囊还在但记录没了"的哑弹。

## 五、部件 2 · 引用源（新方案的地基）

在 DSH 里，"输入框里能变成一个胶囊的东西"必须**先在输入框那儿登记**。

官方自带两个：`@文件`、`@会话`。我们要登记第三个：话布选区。

登记时要交三样东西：

| 交什么 | 作用 |
| --- | --- |
| **名号** | 菜单里那一栏叫什么（如「话布选区」） |
| **候选** | 当前有哪些待引用的选区，每个给一个胶囊的显示文字 |
| **翻译规则** | 胶囊的编号 → **真正发给模型的文字** |

### 胶囊长什么样

| 属性 | 取值 | 说明 |
| --- | --- | --- |
| 显示文字 | 选中文字的前 12 字（超长截断） | 太长会撑爆输入框 |
| 图标 | **文件图标** | 官方只给三种：文件 / 文件夹 / 对话气泡。文件最贴切 |
| 复制文本 | `@文档名 > 选中文字` | 见决策 5（刷新后退化时靠它兜底） |

> ⚠️ **图标只有三种可选**，没有"给话布单独做一个图标"的口子。这不影响使用，但要知道。

## 六、部件 3 · 自动走官方两步

官方留了两个**给程序用**的口子，原话写着：

| 口子 | 官方原话 | 作用 |
| --- | --- | --- |
| 打开菜单 | "传进来的位置是**程序合成的**，而不是用户敲出来的" | 只开话布那一栏 |
| 选中某项 | —— | 走和手点**一模一样**的代码路径 |

所以"自动打 @"这件事，实际做法就是：**话布替你按这两下**。

**这不是钻空子**：官方明确写了这个用途，而且最终插入走的是正门，

和用户自己打 `@`、自己点一下，**是同一条代码路径**。

**收益**：同一个引用源，两种用法 ——

- 点「问 AI」→ 自动走一遍（快到只看见胶囊）
- 想自己挑 → 打 `@`，菜单还在那儿等你

### 实现要点（2026-09-14 取证）

**取会话手柄**：`sessions.scope(sessionId)` → 会话作用域 → `inputTriggers.sessionOf(它)` → 控制器。
其中 `sessionId` 只有**会话作用域**的槽位才拿得到（本插件从 `conversation.input.dock` 那个隐藏桥接件里挂出来）。

**两步**：

```js
controller.toggleSource("话布选区", hit)   // 开菜单（同一个源开着时会 toggle 关掉）
controller.pick("话布选区", 0)             // 选中第 1 条，走的就是用户手点那条代码路径
```

`hit` 是**合成**的，形状照官方 `toggleCommandMenu` 抄：

```js
{ trigger: "@", query: "", quoted: false,
  position: 光标之前全是空白 ? "leading" : "inline",
  span: { start, end, draftRev } }        // 零宽：start === end，口子开在草稿末尾
```

### 🔴 三个坑（都已处理）

1. **候选是异步取的** —— 菜单先 `pending` 再 `ready`，
   而 `pick` 在 ready 之前**静默返回、什么都不做**。
   所以必须轮询菜单状态，等 `ready` 再点（上限 1.2 秒，超时就关掉菜单放弃）。
2. **插进去了没有，不能靠猜** —— 点完隔一会儿数草稿里的胶囊条数
   （官方 `occurrences` 就是"引用出现位置的清单"），条数变多才算成功。
3. **失败必须能退回老路** —— 自动那步返回布尔值，主模块拿 `false` 就照旧塞引用块，
   保证「问 AI」永远有东西可用，不会点了没反应。

> 菜单会闪一下（打开 → 取候选 → 选中），这是异步取候选的必然代价。
> 真机上如果闪得难看，备选方案是绕开菜单**直接插**（略野，见第十二节风险 2）。

## 七、部件 4 · 翻译规则（替代 v2 的注入钩子）

发送时，官方对草稿里每个胶囊调用一次。异步，**官方默认的规矩是"翻译失败就拦住发送"**。

### 正常

```
@"H:/WPSCloud/…/canvas-docs/话布优化.md" > 第十四节 · 第 603 行
「写入方基于哪一版」
```

两行，固定两段式：**@路径 + `>` 短标签** → **原文**。

### 🔴 为什么 `@` 必须打头（2026-09-14 实测确认）

**✅ 已实测**：这样写出来，在对话里会折成一张文件卡片 ——

```
📄 话布优化.md › 第 3 行
「2026-09-12 四轮代码优化的完整记录。目标是…」
```

再长的绝对路径也只占卡片左边那几个字。

**这个形状不能随便动**：

| 要点 | 原因 |
| --- | --- |
| **`@` 放第一个字符** | 折叠靠它。放在第二行或句中就不折，长路径原样铺开（这条主人最先指出） |
| **紧跟 ` > ` 短标签** | 卡片右侧显示的就是这段 |
| **标签里不写文档名** | 卡片左边已经显示文件名了，再写就是「话布优化.md › 话布优化」 |
| **原文另起一行** | 原文可能很长、还可能多行；塞进卡片那一行会把卡片撑爆 |

> 📌 **一度以为折不了**：因为翻遍官方源码也没找到"把消息正文里的 `@"path"` 转成卡片"
> 的解析器（`›` 只出现在前端 vendor 包的 HTML 实体表里），怀疑折叠是"输入框胶囊阶段"
> 的专属效果。**结论是我想多了 —— 正文阶段同样会折。** 记在这里，省得下次再翻一遍源码。

### 🔴 另外三处纯浪费（同一次返工里删掉）

| 浪费 | 具体长什么样 | 处置 |
| --- | --- | --- |
| 文档名与小标题重复 | `引用来源：话布优化 · 话布优化` | 同名时不重复写 |
| **前后文指纹印进正文** | `…话布优化【此处】一、总览 轮次 主题 提交 变更规模 第…` | **删** —— 指纹的用途是第 5 步做过期校验，不是给模型看的 |
| 字符偏移与字数 | `文中第 7 字起，共 66 字` | 删，对模型没用 |

> 指纹那条要特别记：选区落在**表格**里时，摊平后的"前后 24 字"就是一堆列名，
> 纯噪音 —— 而且看起来还挺像正经内容。

### 🔴 定位：引用只留两行，定位交给模型按需来问（2026-09-14 定案）

**问题**：只报「行号 + 原文」定不住位置。主人的原话场景 —— 想把
`1111111111111` 改成 `1111121111111`，可**一行里可能有好几段一模一样的**。
模型拿到"第 3 行 + 原文"仍然只能猜，猜错会**悄悄改到别的地方去**。

**走过的第一版**：把"能唯一定位的一段上下文"直接塞进引用正文 ——

```
@"H:/WPSCloud/…/canvas-docs/话布优化.md" > 第 1 行
「1111111111111」
定位：…乙【1111111111111】（只改【】里的）
```

主人看了两轮之后说：**「这样还是不够优雅，不能通过记录选区来定位吗」**。

**先纠正一个误会**：选区一直有记录（文档 / 原文 / 行号 / 偏移 / 小标题）。
但记录是**我们这边的账**，模型看不到；引用最终要变成**一段文字**发出去，
而模型**认字不认数** —— 给它"第 18 行第 5 字"，它没法核对，只能信或不信。
所以"塞坐标"不是绕远路，而是当时**唯一能让它自己核对**的写法。

**真正该改的是**：把定位**从正文里搬走**，由工具按需回答。

#### 现在的形态：永远两行

```
@"H:/WPSCloud/…/canvas-docs/话布优化.md" > 标题 · 第 18 行 · 多处（第 2 处）
「11111」
```

| 情况 | 标签 | 正文 |
| --- | --- | --- |
| 原文**唯一** | `· 第 18 行` | 两行，一个字都不多 |
| 原文**多处** | `· 第 18 行 · 多处（第 2 处）` | **仍是两行** |

**「第 2 处」是这套设计的关键**：它是**唯一不靠前后文就能说清位置**的信息，
而且**跨端口径一致** —— 渲染前后文字的出现顺序不变，所以客户端（按渲染结果数）
与 host 侧（按 Markdown 源码数）数出来的"第几处"是同一个数。
客户端算不出序数时只标「多处」，**绝不编一个数出来**。

#### 配套：`canvas_locate` 工具（host 侧）

模型看到「多处」这个钩子，就会带着原文 + 序数来问：

| 入参 | 说明 |
| --- | --- |
| `text` | 原文（必填） |
| `path` / `canvasId` | 哪篇文档（引用里给的是**路径**，所以支持按路径认） |
| `ordinal` | 引用标签里的「第 N 处」 |
| `line` | 引用标签里的行号（备用） |

返回**每一处**的源码行号 / 列号 / 带 `【】` 的前后文摘要。定位优先级：

1. **`ordinal`** —— 同一行里也能定住（同一行重复时，行号毫无分辨力）
2. `line` —— 且只有**恰好一处**吻合时才认；两三处都落在附近等于没有线索，一个都不标
3. 都定不住 → 把每一处摆出来让用户确认

**原文已经不在文中** → 明确告知「这段引用已失效」，并禁止照着相似内容猜着改。
这一条**顺带把"过期校验"做掉了** —— 工具读的永远是**当前**文档。

> 📌 **两条硬规矩**：
> 1. **正文里不放坐标** —— 定位不进正文，正文才有资格叫"优雅"。
> 2. **"定不住"就直说，不许猜** —— 宁可反过来问用户，也不能让模型挑一处改，
>    那种错误比"引用没接上"更难发现。
>
> 另：取不到偏移（选区端点不在编辑区内）时，重复次数与序数都记 **0**，不谎报。

#### 走过的弯路（留档，别再犯）

| 弯路 | 为什么被换掉 |
| --- | --- |
| 把"唯一上下文"塞进正文 | 长、难读，而且**照样要模型自己数**；主人一句"不够优雅"否掉 |
| 每一步只试"前后同时扩" | 白带字（`，小明在` 其实一个逗号就够）—— 改成三种扩法取最短，随旧实现一起退休 |
| 换行不处理直接拼 | 选区卡在行尾时，下文那个换行把句尾的省略号顶到下一行（真机截图抓到的） |
| 指纹存起来"给过期校验用" | 没人用 → 已删。过期校验改由工具读当前文档来做，比存指纹直接 |

> ⛔ **旧实现（`anchorFor` / 唯一上下文扩展 / 前后文指纹 / 客户端列号）已整体删除。**
> 需要时从 git 取：`8503a2b`、`52d0ef4`、`1e0619c` 三个提交里是它的完整形态。
>
> 🩸 **这一轮的教训**：我两次都在"怎么把坐标写得更短"上打转，
> 而主人要的是**别把坐标写进正文**。位置编码方式错的时候，优化编码是白费力气。

### 文档被改过之后（已由 `canvas_locate` 承担，不再存指纹）

旧设计打算在引用里存"前后文指纹"，发出之后再比对 —— **现在不需要了**。
模型要定位时本来就要问工具，而工具读的是**当前**文档，
于是两种失效都能当场答出来：

| 情况 | 工具的回答 |
| --- | --- |
| 原文还在，只是行号变了 | 照常返回**现在**的行号与摘要（等于顺手把旧行号修正了） |
| 原文已经没了 | `E_GONE` —— **这段引用已失效**（文档被改过），请用户重新划一次，不要照着相似内容猜着改 |

比存指纹直接：指纹只能回答"变没变"，工具能直接回答"**现在在哪**"。原第 5b 步（过期校验）因此取消。

### 记录找不到（兜底）

```
【话布选区】那段选区的记录已经没了（编号 7）。请让用户重新划一次，不要凭猜测定位。
```

一行。刷新页面后草稿里的旧胶囊会落到这里。

> ⚠️ **翻译规则必须永不抛错。**
> 
> 官方默认"失败就拦住发送"，本意是防止"悄悄降级成复制文本"。
> 
> 但对我们来说，**发不出去比发得不精确更糟** —— 所以主动降级成"带标题的兜底文本"。

## 八、引码去哪了

v2 花了不少篇幅设计 `⟨引码:7⟩` 的外观（外壳字符、生造词）。v3 下它**退居幕后**：

|  | v2 | v3 |
| --- | --- | --- |
| 用户看得见吗 | 看得见，就在输入框里 | **看不见**，藏在胶囊内部 |
| 职责 | 让钩子在**消息文本里**找到它 | 让翻译规则在**记录表里**找到它 |
| 外观还重要吗 | 重要（不能与正文冲突） | **不重要**（它不进正文） |
| 递增编号 | 要 | **要**，理由不变 |
| 进程内不复用编号 | 要（会与输入框里的旧引码撞号） | **仍然要**（旧胶囊可能还没发出去） |
| 重启后清零 | 可以 | 可以 |

**递增编号的理由一个字没变**：随机值理论上会撞号，计数器零成本且绝对唯一。

**外壳字符那一整套设计可以扔了** —— 那是为"在正文里可见但不冲突"服务的，

现在它只在内存表里当货号，用什么符号都行。

## 十五、部件 5 · AI 改完跳过去给你看（2026-09-15）

### 缘起：主人问「难道不能直接在画布上操作吗，直接跳转到选区进行操作」

第七节把定位从"写进引用"改成了"模型按需来问工具"，方向对了。但主人紧接着又问了一句
更根本的：既然选区记着位置，**为什么不干脆跳过去**。

这个直觉补上了前一版最弱的一环：原来"位置对不对"最终是**模型自己判断**的。
跳转可以把判断权**交回给看得见屏幕的人**。

### 🔴 先说清一个容易误解的地方：跳转**不能**替代那个给模型的工具

| | 给谁看 | 怎么用 |
| --- | --- | --- |
| `canvas_locate` 工具 | **模型** | 模型改文档走的是**直接读写文件**，不经过界面 —— 它必须靠工具才知道是哪一处 |
| 「跳过去」（本节） | **主人** | 画布把视图移过去、把那段选中，让人**当场核对** |

**两者解决的是两件事，不能互相替代。** 最初差点按"有了跳转就不用工具了"去做，那是错的：
跳转再花哨，模型那边照样不知道位置。

### 落点：主人选了「改完跳过去给我看」

服务端在 AI 改完文档后记一笔改动，画布端轮询取回来 → 切到那篇文档（如果需要）
→ 在画布里找到改动处 → 滚动过去并选中。**主人当场核对 AI 改对没有**，不用自己翻半天找。

### 怎么知道「AI 改在哪了」

钩子放在 `applyWrite`（`src/host/05-mutations.js`）—— 它是**所有改动的必经之路**，
而且手里同时握着**改前**和**改后**两份完整内容。只有这里才知道改在哪。

改动区间用**最长公共前缀 + 最长公共后缀**算（中间的差集就是改动处）：

- 为什么不用正经的逐行 diff：AI 改话布绝大多数是"整篇 replace、实际只动几处"，
  公共前后缀能**精确圈出**那几处。它唯一的偏差是改动分散在两处以上时会圈得偏大
  （从第一处圈到最后一处），但那种情况跳过去仍然看得见。
- 顺带白拿两个**可靠锚点**：公共前缀的尾部和公共后缀的头部，
  这两段在**改前改后都存在** —— 这正是画布端能拿去找的依据。

**只记 `source === 'ai'` 的改动。** 同一条路还走主人自己的输入
（界面自动保存、外部回写，都是 `'human'`）—— 那些是他自己在改，跳给自己看毫无意义，
还会打断输入。这个 `source` 参数本来就有，正好用上。

### 🔴 坑一：源码里的文字 ≠ 画布上看到的文字

服务端给的是 **Markdown 源码**（`## 标题`、`**粗体**`），画布端手里是 **DOM 渲染后**的文字
（`标题`、`粗体`）。**直接拿去找必然找不到。**

对策：两边**按同一套规则先归一化** —— 把 Markdown 记号（`*_~\`#>|[]()!\`）和空白统统丢掉，
只剩实义字符，再去找。规则一致，两边丢掉的才一致，才能对上。
命中位置再靠一张「每个字符原来在第几位」的映射表换回渲染文字里的真实位置。

> 这也是本项目反复出现的同一个道理的第三次应用：**传文字，不传数字。**
> 位置（第几行第几列）两边口径不同，文字能归一化对齐。

### 🔴 坑二：最小改动区间往往只有 1~2 个字，拿它去找必然撞车

写测试时发现的。公共前后缀算出来的是**最小**区间：

- `散步` → `跑步` 只会圈出 `散` → `跑`（因为 `步` 在两边一样，被算成公共后缀）
- 只换一个字时，区间就只有 **1 个字**

而画布端是拿这段文字**去全文里找**的 —— 1 个字的键满篇都是，
`indexOf` 只会返回**第一次**出现的位置 → **跳到错的地方**。

对策两条：

1. **服务端把搜索键撑开**（`widenSpan`，最少 8 个字，往两边各借一点）。
   反正我们只需要"跳对地方"，不需要"精确到字"。
   ⚠️ 因此记录里的 `added` 是撑开过的，**长度不等于 `addedChars`** ——
   后者报的是真实改动量（老实数），两者用途不同。
2. **画布端先判"唯不唯一"**：拿到全文出现**恰好一次**的那条线索才敢说准；
   三条线索都不唯一时才退回最靠前那条，并在提示里**如实写「请核对」**。
   提示里假装很准，等于骗主人去看错的地方。

### 什么时候**不跳**

这是这个功能最容易好心办坏事的地方，所以定了三条"不跳"：

| 情况 | 处理 |
| --- | --- |
| 主人正在画布编辑区里打字 | **本轮不跳**（跳转会挪走滚动位置、抢掉选区），宁可慢一拍 |
| 三条线索一条都找不到 | **不跳**（宁可不跳，不可乱跳），日志说明原因 |
| 改动落在已关掉 / 已删除的文档里 | 不跳，日志说明 |

另外：一轮里 AI 可能连着改好几处，**只跳最后一条** —— 跳来跳去只会让人晕。

| 文件 | 改动 | 生效 |

| `src/host/05-mutations.js` | `diffSpan` / `widenSpan` / `noteAiChange`，`applyWrite` 里按 `source` 调 | ⚠️ 重启 |

**诊断口**（这个功能最容易"静默不生效"—— 两边对不上时它只是不跳，界面毫无异常）：

```
__ccvSelRefPoll()        立刻问一次服务端，不用等轮询
__ccvSelRefJump(rec)     手工喂一条改动记录，直接看跳转效果
__ccvSelRefSquash(s)     看一段文字归一化之后长什么样（两边对不上时靠它比对）
__ccvSelRefFind(rec)     返回 {pos, unique} 或 null
__ccvJumpOff = true      总开关，排障时临时整体停掉跳转
```

## 十六、部件 6 · 位置主动注入（2026-09-15）

### 缘起：主人说「那我觉得还是要用注入的方式来告诉ai」

上一节把「跳过去给你看」做完了 —— 那是**给你看**的通道。这一节解决另一半：**给机器知道**。

原来的分工是「模型自己来问」：引用标签上写着「多处（第 2 处）」，模型看到就应该调
`canvas_locate` 问一次「到底是哪一处」。但这**靠自觉**。

🔴 真实风险（第九步做完当天就记下的）：
> 模型看到「多处」会不会真去调工具 —— **不调就可能瞎猜，比原来更差**。

瞎猜的后果不是"没帮上忙"，而是**改错地方**：文档里三处一样的文字，它随手挑一处改掉，
界面毫无异常，你过两天才发现改错了。所以不能指望它自觉。

### 关键发现：这件事不用改客户端、也不用加端点

一度以为要「客户端把选区上报给服务端」。查完官方机制发现**完全不用**：

- 官方有个**动态上下文**的口子（`systemPrompt.context`）。注册进去的文本，
  **每一个 step 都会重新求值一次**，然后自动送进模型的上下文。
- 求值时官方会把**当前 agent** 交给我们 —— 顺着 `agent.session` 就能读到这次对话。
- 于是：**用户那条消息里本来就带着引用**，我们只要把它认出来、算好位置、交出去就行。

**一句话**：不新增任何通道，只是把「模型得主动问」改成「我们已经算好放在它手边」。

### 🔴 三个必须踩准的点

1. **求值是同步的**。官方是 `entry.text(context)` 直接调用、没有 `await`。
   返回 Promise 只会被当成一个奇怪的字符串塞进 prompt。所以整条链路必须同步。
2. **找「人说的话」要往前找，不能只看最后一条**。我们自己注入的那条也是
   `user/message`，只看最后一条会看到自己 → 永远解析不出引用。
   做法是**排除法**：跳过一切注入性质的来源（`plugin` / `session-reference` /
   `agent-instructions` / `skill-invocation`），继续往前翻。
   这顺带白捡一个好处：**用户发新的、不带引用的消息时，最近这条就变成它 →
   解析不出引用 → 返回空 → 官方自动把上一条注入抹掉**，不留残影。
3. **绝不抛错**。provider 抛错会毁掉整个 prompt 组装，比不注入严重得多。
   全程 try/catch，任何异常都退化成一件事：**不注入**。

### ⚠️ 生命周期刻意「什么都不做」

**不加 TTL、不自己清、不记状态。** 全部交给官方的替换机制：

| 情形 | 官方行为 |
| --- | --- |
| 用户这轮发了引用 | 文本从空变有 → 推一条注入 |
| 同一轮里模型跑很多步 | 文本没变 → **不重复刷屏**（复用同一条） |
| 下一轮用户没引用 | 文本变空 → 官方把上一条**抹掉** |

自己再叠一套清理逻辑，不是帮忙，是跟官方打架。

### 注入长什么样

它**不是隐形的** —— 会以一行「注入」的样子出现在聊天里（跟时间上下文一模一样，
标签是插件名），点开能看到全文。三种情况：

**只有一处**（说死，不给模型挑的余地）：
```
· 《话布优化》「散步」在第 9 行，**全文只有这一处**：
  …今天又去【散步】了…
```

**多处**（标出目标那一处，其余只报行号 —— 够核对又不啰嗦）：
```
· 《话布优化》「散步」全文共 3 处，**用户要的是第 2 处**（引用标签里写的就是「第 2 处」）：
  ★第 2 处（第 48 行）：…昨天傍晚又去【散步】的习惯一直保持着…
    第 1 处（第 12 行）：…【散步】的习惯要保持…
    第 3 处（第 91 行）：…他坚持【散步】了十年…
  → 动这段文字时照上面标 ★ 的那一处改，别的几处不要碰。
```

**原文已经不在文里了**（最要紧的一种）：
```
· 《话布优化》「散步」，但这段原文**现在全文都找不到了** —— 这段引用已经失效…
  动手前请让用户重新划一次要引用的段落，**不要**去找相似的内容照着改。
```

只有「多处」两个字、没有序数时，**不替模型挑一处**，而是要求它把每处摆给用户确认。

### 🔴 认引用要「只认自己发出的那两种抬头」

引用正文第一行必然是这两种之一：

- `@"D:\…\canvas-docs\话布优化.md" > 小标题 · 第 8 行 · 多处（第 2 处）`
- `【话布选区】话布优化 · 小标题 · 第 8 行`（拿不到真实路径时的退化形态）

**只认这两种**。理由：用户很可能在正文里自己写

```
他说：
「你好」
```

如果宽松匹配，就会**凭空定位一段用户根本没引用的话** —— 然后模型照着改。
所以抬头必须严格校验，认不出就当一个字都没看见。

### 🔴 找文档：宁可认不出，也不拿错文档

**刻意不用** `findCanvasByArg`（`canvas_locate` 用的那个）。它在路径匹配不上时会
**退回"当前活跃文档"** —— 而那很可能**不是**引用说的那一份。拿错文档算出来的位置，
比不注入更糟（模型会去改错误的文件）。

所以自己写了一个严格版：按路径精确匹配 → 不行再用**文件名**兜一次（应对复制粘贴导致
目录不同）→ 都不行就明说"没找到"，让模型先 `canvas_list`。

| --- | --- | --- |

`tools/build.cjs` 按文件名自动收集 `src/host/*.js`，**不用动构建脚本**；
`systemPrompt` 早就在 host 的注入依赖里了（`08-prompt.js` 注册使用指南时就在用）。

定位算法**没有新写一套**：直接复用 `07-tools.js` 里 `canvas_locate` 的

测试里专门有一条对这两者做交叉核对。

### 为什么 `canvas_locate` 不撤

两条路是**互补**的，不是替代：

- **注入** = 提前把答案送到手上（主路径，覆盖绝大多数情况）
- **`canvas_locate`** = 兜底（用户手打的引用、格式怪、解析失败时）

## 十七、部件 7 · 卡片只留文件名（2026-09-15）

主人的原话：

> 这还是有很长一段话啊，可以不可以【二、到底发生了什么 · 第 21 行 · 多处（第 2 处）】
> 这些都不要，都不显示

说的是对话里那张引用卡片 —— 上面那串坐标一直显示着，太长。

### 改成什么样

引用正文从三行收成**两行**，只剩文件名和原文：

```
@"D:\…\话布优化.md"
「散步」
```

行号、小标题、「多处」、「第 N 处」**一个都不写**。

### 🔴 代价：序数没了，"是哪一处"就没有着落了

「第 2 处」这个序数是**划选那一刻按屏幕上第几个算出来的** ——
服务端拿着文档全文也能数出"一共几处"，但**分不出用户划中的是第几处**（屏幕上和源码里的顺序未必一致）。

坐标串一去掉，注入就失去了唯一的线索 → 模型会退回到"只告诉你这段文字出现两处，你自己看着办"。

所以**必须同时开一条上报通道**，两件事是一对，只做一件就是功能倒退：

| 端 | 做什么 |
| --- | --- |
| 客户端 `lib/selref.js` | 划选时（`capture()`）把序数单独 POST 到 `/api/canvas/selref/pin` |
| 服务端 `src/host/09-http.js` | 新端点，把这条记录交给下面的存储 |
| 服务端 `src/host/13-selref-context.js` | 内存里存最近 8 条（`ccvPins`），注入时优先用它拿序数 |

**上报时机选在 `capture()`，不是发送时** —— 划选比发送早得多，天然避开
"消息先到、记录后到"的竞态。上报是**发了不管的**（不 await、失败静默）：
它只是让 AI 知道得更准，失败了顶多退化成"分不出"，绝不能影响用户发消息。

**拿不到上报时**（老客户端没更新、用户手打的引用）：
退回认抬头标签里的序数（兼容），**两个都没有就明说"仅凭行号分不出来"，
绝不替模型挑一处** —— 挑错就是把对的地方改坏，比不注入更糟。

### 🔴 顺带抓到的真缺陷：memo 只按正文做键

`ccvBuildSelContext` 里有一层按正文的 memo（官方每个 step 都调一次，不缓存太浪费）。
原来的键**只有正文**。而"同一段原文在文档里出现多处"时，用户前后两次引用拼出来的
正文**可以一字不差** —— 于是第二次直接命中缓存，序数停在第一次的旧值上。

后果：用户明明划的是第 2 处，模型被告知"用户要的就是第 1 处"，**照着改了错的地方**。
界面毫无异常。

修法：键里带上**上报计数**（`ccvPinSeq`，每收一条上报 +1）和**记录条数**，
任一变化就重算。代价可以忽略 —— 上报只在划选时发生。

发现路径很典型：它是被一条**看起来一模一样的测试用例**逼出来的
（新用例和上一条的正文完全相同，只是上报不同），两个用例的断言互相矛盾才暴露。

### 文件落到哪

| 文件 | 改动 | 生效 |
| --- | --- | --- |
| `lib/selref.js` | 正文只留文件名（VERSION 5）；`capture()` 末尾加 `pinUp()` 上报 | **刷新页面** |
| `src/host/09-http.js` | 新端点 `POST /api/canvas/selref/pin` | ⚠️ **重启** |
| `src/host/13-selref-context.js` | `ccvPins` 存储 + 注入优先取上报 + memo 键修正 | ⚠️ **重启** |
| `tools/test-selref-offset.cjs` | 153 项（+18：正文无坐标、上报真发出去） | — |
| `tools/test-host-selctx.cjs` | 79 项（+18：上报通道、memo 不能挡） | — |

`lib/selref.js` 是**运行期按需拉取**的侧模块（`/api/canvas/selref.js`），
不打包进 `client.js` —— 所以客户端这次**只刷新页面就生效**。
但 host 两处都改了，**必须完全重启 dsh web**。

全套：**406 项通过 / 0 失败**（153 + 69 + 61 + 79 + 44）。

## 十八、部件 8 · 「改了却看不到 / 改了又变回去」（2026-09-15）

主人报来三个累积问题，并给了一句极关键的自述：**「是我点重载了，因为不点重载界面还是不会更新，
就是我点早了。」**

### 🔴 先说教训：我差点拿一份**假证据**去改错代码

主人报的第一条是「通过话布写入返回成功 v2，但磁盘文件没更新」。我写了脚本实测，两次都得到
「文件不存在」—— 看上去完全坐实了「写入不落盘」。

**但那是假的。** 脚本里把含中文的路径**写死**在源码里，PowerShell 按系统 ANSI 解析这份脚本，
中文路径变成乱码 → 去查一个根本不存在的路径 → 当然"不存在"。

改成「路径从接口响应里取」（响应是 UTF-8，不经过脚本源码）之后，同一件事立刻反转：

```
write -> {"ok":true,"version":2}
md appeared after 1.5s len=16 content=[P3-ALPHA-CONTENT]
```

**写入是好的**，1.5 秒防抖后正常落盘，meta 也同步更新，删除也正常。

> 教训很硬：**「查不到」和「不存在」是两回事。**
> 任何"找不到文件 / 没反应 / 没生效"的实测结论，先验一遍**读数方法本身**对不对
> （路径、编码、权限、时机），再下结论。否则会照着幻象修代码。
> 这条和技能里「验证前先确认锚点类真的在」是同一类错误。

### 真正的问题：重载把主人刚敲的字**取消**掉了

代码里的病灶就一行（`loadCanvas` 开头）：

```js
clearTimeout(saveTimer.current);   // 防竞态：切换前丢掉旧文档的待写自动保存
```

这行的**用意**没错（切换文档时要防响应乱序），错在**只取消、不落地**：

1. 主人敲字 → 草稿进浏览器本地 + 起了个「1.5 秒后写服务端」的定时器
2. 主人想看看最新版 → **1.5 秒内**点了「重载」
3. 定时器被这行清掉 → 刚敲的内容**不会写出去**
4. 紧接着用服务端内容覆盖界面 → **主人眼看着他刚写的东西变回旧的**

他说的「改了却看不到 / 改了又变回去」，就是这条路径。而且全程**没有任何报错**。

### 修法

| 改动 | 做什么 |
| --- | --- |
| 新增 `flushPending()` | 重载/切走前，**先亲手把待写内容写出去**，再拉服务端（`clearTimeout` 保留，但不再只管取消） |
| `loadCanvas` 拆出 `doLoad()` | 先 flush，flush 完再决定要不要加载 |
| **冲突时不清屏** | 本机有编辑、服务端也前进了 → 保留界面不动，只提示一次，留哪份由主人定（此前是直接覆盖） |
| `writeMd` 加 `still` 判断 | 「切走前先落一次」的响应可能晚于新文档加载，不能再把**旧文档**的版本号盖到**新文档**身上 |

### 顺带修掉的两个隐患

**1. AI 写入不再等那 1.5 秒**

防抖是为「人在连续打字」准备的（把一串输入合并成一次写）。**AI 一次改动就是一次**，
没有可合并的东西，等 1.5 秒只有坏处 —— 主人改完马上去看磁盘、或让别的工具读这个文件，
看到的还是上一版，会以为"根本没写进去"。这是**静默的误导**。

所以 `applyWrite` 里分流：`source === 'ai'` → 立刻落盘（失败也不影响内存结果，防抖那次还会兜底重试）；
人的输入照旧走防抖。

**2. 落盘串成一条链**

`saveCanvas` 是异步的，写的是 `c.content`。两次写一旦并发，「第二次先完成、第一次后完成」，
文件最后会停在**旧内容**上 —— 而且两边都报成功，没人会发现。加 `saveSerial()` 把它们串起来，
顺序就是调用顺序。链本身不因某一次失败而断（后面的写该发还得发）。

### 另两条的现状（都已在之前的会话里修掉，本次实测复核）

| 主人报的 | 现状 |
| --- | --- |
| 重启后产生同名重复画布 | `restore()` 按路径去重（先到先得）+ `loadFileDoc` 同文件复用，两道防护都在；**实测清单 8 条、零重复** |
| 面板显示的路径是硬拼的 | `canvasMdPath()` 已改为返回**绝对路径**，`/api/canvas/list` 等三处端点都用它；前端只在拿不到路径时才退回相对形式兜底 |

### 测试

## 十九、部件 9 · 「发一条有胶囊，再发一条胶囊全没了」（2026-09-15）

主人报：**发一条引用会显示胶囊，发多条就不显示胶囊了。**

### 日志给出的证据

```
[selref] 已记录选区 #1 … 7 字「文件在的地方，」
[selref] 自动插入：打开「话布选区」菜单（草稿 0 字，版本 0）     ← 草稿空
[selref] 自动插入成功：胶囊已进输入框                        ✅

[selref] 已记录选区 #2 … 7 字「出问题的地方叫」
[selref] 自动插入：打开「话布选区」菜单（草稿 42 字，版本 1）    ← 草稿已有内容
[selref] 自动插入没成：菜单没打开（或被立刻关掉了）              ❌
```

**唯一的差别就是草稿里有没有东西。** 草稿空时一切正常，非空就失败。

### 🔴 更糟的不是失败，是「失败之后干什么」

失败会退回老做法（往输入框塞纯文本）。而那条老路是这么写的：

```js
var curDraft = window.__ccvInputState.draft          // ← 这是**纯文本**
window.__ccvInputActions.setDraft(body + '\n\n' + curDraft)   // ← 整体重写
```

`draft` 是**纯文本**，胶囊在它里面的样子只剩 `@标题 > 摘要`。
**用纯文本整体重写草稿 = 把已经插进去的胶囊全部拍平成文字。**

所以主人的体感是「再发一条，胶囊全没了」—— 第二次插入不但自己没成胶囊，
**还顺手毁掉了第一次的**。这是本次最该修的地方。

### 修法：能救则救，别急着降级

| 改动 | 为什么 |
| --- | --- |
| 给「打开菜单」加 **600ms 宽限** | 原来 `toggleSource()` 之后**同步**看一眼快照，没开就直接判失败、连轮询都没起。只要菜单是"晚一拍"才出现在快照里，就必然踩中 |
| 失败后 **重试一次**（隔 300ms） | 重试只多等几百毫秒；降级的代价是**毁掉主人前面所有的引用**，划不来 |
| 失败时把现场记全 | 主人开不了控制台，日志是唯一诊断通道。原来只记「没打开」四个字，下次照样查不出原因 |

顺手把「打开菜单」那行日志补上**口子位置 / leading 还是 inline / 已有几条胶囊** ——
万一下次还失败，这四项直接指向原因，不用再猜。

### 一个还没修的隐患（记下来，暂不动）

胶囊被拍平后的样子是 `@标题 > 摘要`。而注入那边**只认自己发出的两种抬头**
（`@"绝对路径"` 和 `【话布选区】`）—— 拍平形态**两种都不是，认不出来**。

后果：走了降级的那条引用，位置注入对它无效（引用文字还在，AI 只是不知道是哪一处）。

**为什么现在不改**：让注入多认一种抬头，就会把"用户自己在正文里打的 `@某文件 > 说明`"
也认成引用 —— 而**凭空定位一段没被引用的文字**是本方案里最不能犯的错（见第十六节）。
真要修，得先把拍平形态改成规范形态（`@"路径"` + 换行 + `「原文」`），
那是动 `clipboardText`，影响的不只是这一个场景。**等宽限 + 重试上线后观察，降级是否还会发生再说。**

## 二十、部件 10 · 第二条引用：不再开菜单，直接派发官方事件（2026-09-15）

主人第二次数同一个毛病：**「第二条还是会把已经做好的胶囊压成一堆普通文字」**。

→ **上一版的修法（给菜单加 600ms 宽限 + 失败重试一次）没打中。**
说明失败的原因不是"菜单开得慢"，而是**菜单会被关掉，且关掉是必然而不是偶然**。

### 真因：菜单开着就会被下一次输入状态刷新带关

读官方 `InputTriggerController` 源码（`dsh-client-ui-input-trigger/lib/client.js`）得到的事实：

| 事实 | 出处 |
| --- | --- |
| 每次草稿/光标变化都会调 `track(...)`，它开头就 `clearLauncher()` | `track()` 第 332~333 行 |
| `track()` 里若"检测不到触发器"，直接 `reduce({type:"close"})` → **菜单关** | 第 335~339 行 |
| 程序化打开的菜单（`toggleSource`）不会在草稿里留下 `@` 字符 | 我们的 hit 是**合成**的 |
| 所以只要有任何一次输入状态刷新路过，菜单必被关 | — |

草稿为空时"没有变化可刷新"，所以侥幸成功；草稿里有内容时刷新更频繁 → **必然失败**。

**结论：这条路的结构性问题是"开着一个什么东西等它别被关掉"。不该在这里继续加固。**

### 正路：官方把"插入胶囊"做成了一个会话级事件

同一份契约里写着（`dsh-client-ui-conversation/lib/types/client/contract/input.d.ts`）：

```ts
/** Insert a structured reference into the scoped input machine.
 *  @mode bail */
'slash/input-insert-reference'(request: InsertReferenceRequest): true | undefined;
```

关键三条：

1. **这是给业务插件的口子** —— 契约原文：「the scoped input events carry the mutation verbs」
   （业务包看到的是 InputState，**改动动词走这些会话级事件**）。
2. **处理体就是最终函数** —— `actx.on("slash/input-insert-reference", (req) => shell.insertReference(req.reference, req.span))`。
   跟"用户自己打 @ 再点一下"落到的是**同一个 `insertReference`**，走正门，不是绕后门。
3. **带草稿版本校验** —— `if (span.draftRev !== this.rev) return false`。
   版本对不上就拒绝执行，**这是保护不是障碍**（拒绝总比插到错的地方强）。

派发方式照抄官方 `execute()`：`actx.bail(actx, 事件名, 请求)` —— 第一个参数是派发主体。
`actx`（会话作用域）本来就在手（`sessions.scope(sessionId)`，早先为了拿菜单手柄已经在用）。

### 🔴 零宽 + 落在末尾：不破坏已有内容的关键

官方是"**把 span 换成胶囊**"。所以我们的 span 一律是：

```
{ start: 草稿长度, end: 草稿长度, draftRev: 现读 }
```

起止相同 = **零宽** = 等于在末尾**追加**。前面已有的胶囊一个字都不会动。

这条是本次修复的**核心不变量**，专门写了用例钉住 —— 以后谁把 span 改成"替换整段草稿"，
测试立刻红。

### 三条路，从稳到退；以及一条硬规矩

| 顺序 | 走法 | 说明 |
| --- | --- | --- |
| ① 首选 | **直接派发** `slash/input-insert-reference` | 不经菜单，没有"被关掉"这回事 |
| ② 次选 | 走菜单替你点一下（老路，带重试） | 留着兼容更老的 DSH（事件派发不出去时还能用） |
| ③ 兜底 | **派发** `slash/input-insert-text` 往末尾追加纯文字 | 同样是官方事件、同样零宽只追加 |

🔴 **硬规矩：草稿里已经有胶囊时，绝不许整体重写草稿（`setDraft`）。**

理由：`InputState.draft` 的官方定义就是「**胶囊展开成 clipboard 形态**的纯文字投影」。
拿它整体重写 = 把胶囊按纯文字填回去 = **拍平**。
所以主模块的兜底顺序被改成：

1. 先请侧模块走③（追加，不动已有内容）
2. 一个胶囊都没有 → 才允许整体重写（此时重写等于"填一份纯文字"，无害）
3. 有胶囊又插不进去 → **什么都不做**，弹一句话告诉主人，让他再点一次

**宁可这次没插上，也不能弄坏他前面的引用。** 后者是他真正的损失，而且界面上毫无异常。

### 顺带：那个"故意未修的隐患"基本消失了

第十九节记下的隐患是"拍平形态 `@标题 > 摘要` 注入认不出"。
现在产生拍平形态的那条路（整体重写）已经被挡住，**这个隐患几乎不会发生了**。
（但如果将来真出现拍平形态，注入仍认不出 —— 那部分结论不变。）

## 二十一、部件 11 · 第二条引用插不进的**真正**原因：官方有两套坐标（2026-09-15）

### 主人给的现场线索

> 插入第二条失败，但是我手动 @ 可以引用第二条

**这一句就是破案的关键。**

- 手动打 `@` 能插进去 → **编辑器本身没问题**，胶囊节点能创建、能落地。
- 那失败就一定出在"**我们给的位置**"上，而不是权限、时机或版本号。

（前两次都在往"菜单被关掉"这个方向查 —— 第二十条为此把菜单整条路换掉了。
换掉之后失败依旧，说明菜单只是**其中一个**原因，不是全部。）

### 读官方源码找到的两套坐标

| 投影 | 名字 | 一颗胶囊占几个字 | 谁在用 |
| --- | --- | --- | --- |
| **剪贴板投影** | `clipboardText` | **一整串**（`@标题 > 摘要`） | 发布给插件的 `InputState.draft` |
| **探测投影** | `detectText` | **1 个字**（`\uFFFC`） | 事件里的 `span`（`insertReference` / `insertText` / `beginCommand`） |

出处（`@deepseek-ai/dsh-client-ui-conversation`）：

- `$composerLayout()` 里 `pushLeaf("chip", kid, "￼", kid.getTextContent())`
  —— 第三个参数是探测形态（1 个字），第四个是剪贴板形态（整串）。
- `compose()` 发布 `draft: this.projection.clipboardText` —— **插件只拿得到剪贴板投影**。
- `insertReference(ref, span)` 里 `this.projection.detectText.slice(span.end, span.end + 1)`
  —— **它按探测坐标解释 span**。

### 为什么这会造成"第一条永远成，第二条永远不成"

```
草稿里没有胶囊：  draft.length === detectText.length   → 位置算对了 → 成功
草稿里有一颗胶囊：draft.length 比 detectText.length 大「胶囊串长 − 1」
                  → 我们报的"末尾"越过了文末 → 官方 applyEdit 落不下来 → false
```

**这是必然失败，不是偶发。** 也正好解释了为什么"就第二条不行、手动就行"。

### 修法：按公式把剪贴板坐标折成探测坐标

```
探测末尾 = draft 长度 − Σ(每颗胶囊的 length − 1)
```

`InputState.occurrences[].length` 就是那颗胶囊在剪贴板投影里的长度
（官方 `$projectComposer` 给的是 `clipboardLength`）。

- 对照官方辅助函数 `detectOffsetOfClipboardOffset`：偏移落在最末尾时返回的正是 `detectLength` ✅
- **没有胶囊时公式结果与从前完全一致** → 不会把原本好好的第一条弄坏
- 负数夹到 0（`length` 万一离谱也不至于把位置算飞）

### 顺带推翻了一条旧结论（重要）

第二十条（以及再上一轮）都把"第二条失败"归因于**菜单会被输入状态刷新带关**。
那个现象**是真的**，但它只是"第二条失败"的**次要**原因。
真正的充分原因在坐标上 —— 所以**只换菜单这条路，永远治不好它**。

教训：**换掉一条通道之前，先确认原通道失败的机理与自己以为的一致。**
我这次是"看到一个真现象 → 当成唯一原因 → 换掉整条路 → 问题还在"。

## 二十二、部件 12 · 位置提示与引用对上号：改读「队列」记录（2026-09-15）

### 缘起：主人问「位置提示和引用能不能建立对应关系，防止再出现错误」

这正是第二十一节末尾那条**刻意没修**的缺陷。主人真机复测后（两条引用都能插进去了、
说明第二十一节的坐标修法生效），他直接点出这条：注入讲的还是**上一轮**的事，
必须让"位置提示"和"这次的引用"真正对上。

### 🔴 真因：官方把用户消息挂到"界面"上的时机，晚于我们求值的时机

上一节猜的方向（"这条消息可能还没进 `session.surface.nodes`"）是对的，
但原因不是网络慢或缓存，而是官方 agent loop 的**固定执行顺序**。读 `dsh-agent-loop`
的 `preStep`，一个 step 里依次做三件事：

| 顺序 | 做什么 | 我们要的东西在哪 |
| --- | --- | --- |
| ① | 认领待处理的消息（claim） | — |
| ② | **组装系统提示词** | 👈 **我们的 provider 就在这里被求值** |
| ③ | 把这条消息追加进界面（`session.append('user/message', …)`） | 👈 但我们**已经在第 ② 步读完了** |

所以**第 1 个 step 永远读不到刚发的那条** —— 此刻"最近一条人消息"只剩上一条。
到第 2 个 step，第 ③ 步早就做完了，于是"追上了"。这正好解释了那张时刻表：
第 1 步晚一条、第 2 步正确。

**这不是偶发，是每次都必然发生。**

### 关键发现：这条消息其实**有**更早的记录，只是记录在另一本账上

官方 `ReactLoopInbox.mutate` 在**收到消息的那一刻**就发了一条会话事件：

```
agent/inbox/spliced → { target, start, inserted: [message, …] }
```

这条事件**发生在第 ③ 步之前**，所以第 1 个 step 就能读到。
它就是"这个 step 真正要处理的那条消息"的权威记录。

官方自己的 `RuntimeContextProjection` 也是从事件流（而不是只看界面）里读最近一条
`user/message` 的 —— 说明"读事件流"本来就是官方自己的做法，不是我们绕路。

### 修法：两条通道都读，取新的那条；再加一道"否决"

**第一，两通道求值。**

- **队列通道**：翻会话事件，找 `agent/inbox/spliced`，从 `data.inserted` 里取人消息。
- **界面通道**：原来那条路（翻 `surface.nodes`），保留不动。

两者各带一个时间戳，**谁新信谁**。这样第 1 步由队列通道兜住（不再晚一条），
第 2 步两通道都到齐、取新的即可（结果一致，不会来回抖）。

**第二，队列通道用"白名单"，不用界面通道那套"黑名单"。**

界面通道是"排除掉已知的非人消息"；队列里除了人消息，还会混进工具结果的补充上下文
这类东西。**黑名单会漏，白名单不会** —— 队列通道只认 `source.kind === 'user'`，
不是就继续往前翻。

**第三，一道保险：读不到队列、只能看界面时，加时间戳否决。**

万一队列通道读不到（官方改版、事件被裁掉等），就只剩界面通道。此时若
**最新一条 pin 的时间晚于我们读到的那条消息的时间**，说明我们读到的消息是旧的
→ **本轮干脆不注入，也不能注入一条指向上一轮的错信息**。
（第 2 步会自动补上，所以"少说一次"不丢信息。）
宁可不说话，也不说错话 —— 这与 750 行那条"认不出就不注入"的原则是同一条。

**第四，顺手补掉一个会"指错地方"的漏洞：同一条消息里的两条引用不能抢同一处。**

一条消息里可能引同一段原文两次（被 `「」` 截开的）。原来按"路径 + 原文"找位置，
两次都会命中**同一条**位置记录 → 两条引用被指向同一处。
现在给查找加了一个"本次组装里已经用掉的记录"名单，**用过的跳过，往下找下一条**。

### 🔴 为什么要给"新通道"单独开一本日志

这次的 bug 属于**时序类**，静态看代码看不出来，而主人开不了控制台。
所以给服务端也加了一本日志（`%TEMP%/ccv-selctx.log`，与客户端那本 `ccv-selbar.log` 分开），
每次组装记一行：**走的是哪条通道、读到的时间戳、pin 有几条**。

这本日志是"能否定位下一层问题"的关键 —— 没有它，下次再出现类似现象，
依然只能靠猜。

## 附录 · 外部改盘的已知问题（2026-09-14 实测）

**现象**：在磁盘上直接改 `canvas-docs/*.md`，话布看不到；点「重载」也看不到。

**原因**（读码确认）：

1. 话布**只在启动时**把文档从磁盘读进服务端内存（`restore()`）。
2. 前端「重载」= `GET /api/canvas/read` → 返回的是**内存里的 `c.content`**，

**不读磁盘**（按钮自己的提示语也写着"AI 在对话里改过话布后用它同步"）。

1. 反向却是通的：内存里有 `dirty` 记录时，会在防抖 / 关闭时**写回磁盘**（`flushDirty` → `saveCanvas`）。

**后果**：内存里的旧版会**无声覆盖**磁盘上的新版。本次实测就发生了 ——

外部改的 v3 在 19:59 被内存中的 v2 覆盖回磁盘。

**规避（当前）**：外部改完文档后，**先不要打开/编辑话布里的该文档**，直接重启 DSH，

让 `restore()` 从磁盘读入新内容（此时内存 `dirty=false`，不会再回写）。

**建议（待做）**：

- 给「重载」增加"比对磁盘 mtime / 顺便读盘"的行为，或另加「从磁盘重读」
- 或在 `saveCanvas` 前做一次磁盘 mtime 比对，发现外部改动就提示冲突（复用现有 `knownVer` 冲突通道）
